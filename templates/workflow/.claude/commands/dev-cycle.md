# /dev-cycle - 이슈 기반 개발 사이클

`$ARGUMENTS`의 이슈를 기준으로 조사, 계획, 구현, 검증과 보고서 초안까지 진행한다. 저장소 루트의 `dev-cycle.config.json`을 먼저 읽고 저장소명, 기준 ref, 지침 경로와 프로젝트 명령을 사용한다.

## 진행 순서

1. 이미 존재하는 이슈 번호와 범위를 조회한다. 번호가 없으면 확인하며 새 이슈는 만들지 않는다. 설정의 저장소와 실제 작업 저장소가 일치하는지 확인한다.
2. researcher로 현재 코드와 요구사항을 조사한다.
3. planner로 변경 파일, 단계, 위험과 검증 계획을 만든다. 작업 자체가 이미 승인됐다면 계획을 공유하고 진행하며, 승인되지 않은 구현이나 범위 확대라면 구현 전에 결정을 받는다. 외부 `grill-me`가 설치된 경우 사용자가 직접 호출할 수 있으며, 없으면 일반 질문으로 대체한다.
4. 현재 작업 트리와 브랜치를 확인해 기존 변경을 보존한다. `paths.conventions`의 브랜치 규칙과 `defaultBranch`를 기준으로 작업 브랜치를 준비한 뒤 계획과 승인 범위 안에서 구현하고 테스트 코드를 함께 작성한다. 기본 브랜치에 직접 구현하지 않는다. 브랜치 규칙/기준 ref가 없거나 기존 변경 때문에 안전하게 전환할 수 없으면 구현 전에 그 문제를 보고한다. 승인된 로컬 구현과 실패 수정은 반복 확인 없이 이어간다.
5. `/test`를 사용한다. dev-cycle CLI의 test 기능이 아직 설치되지 않았으면 설정의 `commands.test`에 있는 실행 파일과 인자 배열을 그대로 실행하고 실제 종료 결과만 기록한다.
6. reviewer로 `baseRef` 또는 `defaultBranch` 기준 변경을 검토한다. 지적과 근거를 보고하고 승인된 범위 안의 명백한 수정은 이어서 반영한 뒤 다시 검증한다. 새 설계 선택이나 범위 확대가 필요한 지적은 분류해 결정받은 뒤 반영한다.
7. `/wrap-up`으로 확인된 변경과 검증 결과를 정리한다. dev-cycle CLI의 report 기능이 설치된 경우에만 실행 기록 기반 초안을 사용한다.
8. 커밋, push, PR 게시, 리뷰 답글과 머지는 사용자가 요청한 범위에 포함된 경우에만 수행한다.

## 원칙

- Claude Code는 조사, 계획, 구현과 리뷰 판단을 맡는다. CLI는 템플릿 설치, 테스트 실행과 실제 기록 기반 보고를 맡는다.
- `PreToolUse` 또는 명령 호출 로그는 실행 완료나 성공의 증거가 아니다. 실제 프로세스 종료와 해당 실행의 결과를 근거로 한다.
- 작업 메모는 재개 보조 자료이며 Git 상태, 이슈와 실행 기록보다 우선하지 않는다.
