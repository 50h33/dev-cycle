# dev-cycle Claude Code 워크플로

`dev-cycle init`은 이 템플릿에 포함된 Claude Code 에이전트, 명령, 스킬, 작업 메모 형식을
대상 저장소에 설치합니다. 조사, 계획, 구현, 리뷰 판단은 Claude Code가 맡습니다. dev-cycle
CLI는 템플릿 설치, Gradle 변경 영향 테스트, 실제 실행 기록, 기록 기반 report 생성을
담당합니다.

## 구성

| 구성 | 역할 |
| --- | --- |
| `researcher` | 구현 전 코드와 외부 근거 조사 |
| `planner` | 변경 대상, 단계, 위험과 검증 계획 작성 |
| `reviewer` | 제품 코드 변경의 문제와 위험 검토 |
| `gardener` | Claude Code 템플릿, 설정과 문서 정합성 점검 |
| `/dev-cycle` | 이슈 확인부터 로컬 구현, 검증과 요약까지 연결 |
| `/test` | 실제 테스트 실행과 결과 보고 |
| `/review-pr` | 원격 PR 리뷰 코멘트 제안 |
| `/resume` | 작업 메모와 Git 상태를 읽는 재개 안내 |
| `/wrap-up` | 확인된 로컬 작업과 검증 결과 요약 |
| `issue`, `pr`, `apply-review` | 요청 범위 안에서 GitHub 작업 수행 |

개인 권한 파일, 실제 로그와 작업 메모는 템플릿에 포함하지 않습니다.

이 문서의 `dev-cycle` 표기는 CLI 호출을 뜻합니다. 소스에서 빌드했다면 `dev-cycle` 대신
`node /path/to/dev-cycle/dist/cli.js`를 사용하고, Claude Code에도 빌드한 CLI의 실제 경로를
알려 주세요. `init`은 CLI를 PATH에 등록하지 않습니다.

## 프로젝트 설정

`git rev-parse --show-toplevel`로 확인한 대상 Git 루트의 `dev-cycle.config.json`을 프로젝트
설정으로 사용합니다. 하위 디렉터리에서 시작해도 상대 경로와 명령의 작업 디렉터리는 이
루트를 기준으로 합니다. Git 저장소가 아니거나 루트를 확인할 수 없으면 경로를 추정하지
않습니다.

```json
{
  "schemaVersion": 1,
  "repository": "owner/repository",
  "defaultBranch": "trunk",
  "baseRef": "origin/trunk",
  "paths": {
    "conventions": "AGENTS.md",
    "issueTemplates": ".github/ISSUE_TEMPLATE",
    "prTemplate": ".github/pull_request_template.md"
  },
  "commands": {
    "test": {
      "executable": "./gradlew",
      "args": ["test"],
      "windows": {
        "executable": "./gradlew.bat",
        "args": ["test"]
      }
    }
  },
  "test": {
    "commonModules": [],
    "fullTestPaths": ["build.gradle", "settings.gradle", "gradle/"],
    "documentationPaths": ["docs/", "README.md"]
  },
  "artifactsDir": ".dev-cycle"
}
```

- `schemaVersion`은 반드시 `1`이어야 합니다.
- `repository`는 `owner/name` 형식의 GitHub 저장소 식별자입니다.
- `defaultBranch`에는 브랜치 생성과 PR base에 사용할 짧은 브랜치 이름을 입력합니다. `HEAD`나
  `refs/heads/` 같은 접두사는 넣지 마세요. `baseRef`에는 `HEAD`를 명시할 수 있습니다.
- `baseRef`는 변경 비교 기준입니다. 생략하면 `defaultBranch`를 사용하며 ref를 임의로
  fetch하거나 추정하지 않습니다.
- `paths`에는 Git 루트 기준 상대 경로를 입력합니다.
- `commands`의 각 명령은 `executable`, `args`, 선택적인 `windows` 설정으로 구성합니다.
  값을 단순히 연결하거나 eval하지 않습니다. argv 인터페이스가 없으면 `/test`의 shell 인용과
  미실행 처리 규칙을 따릅니다.
- `test.commonModules`와 영향 경로는 저장소에 맞게 설정합니다. 특정 이름을 공통 모듈로
  가정하지 않습니다.
- `fullTestPaths`와 `documentationPaths`는 glob이 아닙니다. 파일 경로는 정확히 일치해야 하고,
  `/`로 끝나는 항목은 해당 디렉터리 아래의 모든 경로와 일치합니다.
- 경로가 겹치면 전체 영향 경로와 공통 모듈 판정을 문서 생략보다 먼저 적용합니다. 문서 경로에
  포함됐다는 이유로 빌드 설정 변경을 생략하지 않습니다. 분류할 수 없는 변경은 전체 테스트로
  확대합니다.
- `artifactsDir`는 CLI 전용 상대 디렉터리입니다. 저장소 루트 밖이나 기존 소스, 배포 파일과
  겹치는 경로를 지정할 수 없습니다. 기본값이 아닌 경로를 사용하면 해당 경로도 Git에서
  제외하세요.

다른 프로젝트 명령은 `commands`에 같은 구조로 추가할 수 있습니다. 설정하지 않은 명령을
추정해 실행하지 않습니다. `commands.test`는 필수입니다. Windows 설정이 있으면 executable과
args를 모두 그 값으로 바꿉니다. `paths`, 테스트 영향 경로, `artifactsDir`는 `/`로 구분하세요.
저장소 밖 경로, glob, Windows 예약 이름은 사용할 수 없습니다. 실행 파일에는 PATH의 명령
이름, Git 루트 기준 상대 경로, 명시한 절대 경로를 사용할 수 있습니다.

## init 설치와 기존 파일 보존

`dev-cycle init`은 배포 manifest에 등록된 공유 파일만 대상 Git 루트에 설치합니다. 먼저
`--dry-run`으로 모든 파일의 생성, 유지, 충돌, 오류 상태를 확인하세요. dry-run은 대상 파일과
디렉터리, Git 설정, 로그, 메모를 변경하지 않습니다. 충돌이나 사전 검사 오류가 하나라도
있으면 새 파일도 쓰지 않습니다.

기존 CLAUDE.md, settings.json, 스킬, .gitignore의 내용이 다르면 덮어쓰거나 자동으로
합치지 않습니다. `.gitignore`는 렌더링된 제외 블록 전체를 기존 파일 끝에 직접 추가하면
재실행할 때 유지된 파일로 처리합니다. 다른 공유 파일을 사용자가 합치면 계속 충돌할 수
있습니다. 프로젝트 규칙은 `paths.conventions`가 가리키는 별도 문서에 두고, 개인 권한은
`settings.local.json`으로 분리하세요. 개인 권한 파일과 실제 메모/로그는 설치하지 않습니다.
필요한 개발 도구나 실행 파일, 저장소 지침, 이슈/PR 양식은 대상 프로젝트에서 준비하세요.
설치 후 대상 Git 루트에서 Claude Code를 열고 `/agents`로 역할을 확인한 뒤 `/resume` 또는
`/dev-cycle <이슈 번호>`를 사용하세요.

## 에이전트, 명령과 스킬의 차이

에이전트는 한 가지 역할에 집중합니다. `researcher`는 조사, `planner`는 계획, `reviewer`는
제품 코드 검토, `gardener`는 워크플로 구성을 점검합니다. Claude Code에서 에이전트를 직접
선택해 특정 단계만 맡길 수 있고, `/dev-cycle`을 사용하면 필요한 역할을 순서대로 호출합니다.

한 역할에는 한 책임을 맡깁니다. 조사와 계획, 검토 결과는 메인 대화로 돌려받고 실제 구현과
수정은 메인 대화에서 진행합니다. 이렇게 나누면 구현 과정에서 세운 가정과 별도로 코드를
검토할 수 있습니다. 새 역할이 필요할 때는 기존 역할과 책임이 충돌하는지, 조사 결과를 별도로
정리해야 하는지, 필요한 도구 권한을 더 좁혀야 하는지부터 확인하세요.

명령은 반복되는 작업 순서를 실행합니다. `/dev-cycle 123`처럼 이슈 번호를 전달하거나,
`/test`, `/resume`, `/wrap-up`처럼 현재 저장소 상태를 기준으로 실행합니다. 스킬은 대화의
요청과 문맥에 따라 호출되는 절차입니다. 이슈 작성, PR 작성, 리뷰 반영을 요청하면 각각
`issue`, `pr`, `apply-review` 스킬이 저장소 설정과 양식을 확인합니다.

명령과 스킬은 Claude Code 대화에 입력합니다. 스킬도 `/issue`, `/pr`, `/apply-review`로
직접 지정할 수 있습니다. 터미널에서 실행하는 `dev-cycle test`나 `dev-cycle report`는 CLI
명령이며, `/test`와 PR 스킬이 실제 실행과 기록 확인에 사용합니다.

공유 `.claude/settings.json`은 plan을 기본 권한 모드로 설정합니다. 계획을 검토한 뒤 구현하도록
돕는 기본값이며, 사용자가 이미 승인한 로컬 작업이나 실패 수정까지 매번 다시 승인받으라는
뜻은 아닙니다. 범위 확대, 되돌리기 어려운 변경과 요청되지 않은 외부 게시처럼 새로운 결정이
필요할 때만 확인합니다.

## 역할별 에이전트

에이전트 이름과 맡길 일을 대화에서 함께 지정하세요. 다음은 각각 따로 사용할 수 있는 요청입니다.

```text
researcher로 이 이슈와 관련된 코드와 테스트를 조사해 줘.
planner로 조사 결과를 바탕으로 구현 계획을 세워 줘.
reviewer로 현재 브랜치의 변경을 검토해 줘.
gardener로 Claude Code 설정과 문서의 불일치와 깨진 링크를 점검해 줘.
```

### researcher: 구현 전 조사

구현 위치, 관련 규칙과 기존 패턴을 먼저 파악할 때 사용합니다. 저장소와 외부 자료에서 확인한
사실에 파일 위치나 URL을 붙이고, 확인한 사실과 추정을 나눠 보고합니다. 코드를 수정하거나
설계를 결정하지 않으므로 조사 결과는 planner의 입력으로 사용합니다.

### planner: 구현 계획

조사가 끝난 뒤 변경할 파일, 작업 순서, 영향 범위, 위험, 롤백과 검증 방법을 정리합니다. 구현은
하지 않습니다. 아직 정하지 않은 설계나 범위 확대가 있으면 사람의 결정 사항으로 분리하고,
이미 요청에 포함된 작업은 다시 질문하지 않습니다.

### reviewer: 구현 후 독립 검토

`baseRef` 또는 `defaultBranch`와 현재 작업 트리의 차이를 읽고 정확성, 설계, 오류 처리, 보안,
동시성, 성능, 테스트 가능성과 저장소 규칙을 검토합니다. 지적은 Must, Should, Nit으로 나누고
파일의 실제 위치와 개선 방향을 함께 보고합니다. reviewer는 코드를 직접 수정하지 않으므로
타당한 지적은 구현 단계에서 반영하고 다시 테스트합니다.

- Must: 완료 전에 해결해야 하는 문제입니다.
- Should: 위험을 줄이거나 품질을 높이기 위해 반영을 권하는 개선입니다.
- Nit: 동작에 미치는 영향이 적은 표현·가독성 수준의 제안입니다.

확인된 문제가 없으면 검토한 범위와 아직 확인하지 못한 부분을 보고합니다.

### gardener: 워크플로 유지보수

제품 코드 리뷰와 별도로 Claude Code 에이전트·명령·스킬, 문서와 설정의 불일치, 깨진 링크,
사용하지 않는 항목, 과도한 개인 권한, 추적되면 안 되는 로그와 메모를 점검합니다. 결과에는
심각도와 정리 방향을 적지만 직접 수정하지 않습니다. 워크플로 파일을 추가하거나 변경한 뒤,
또는 문서와 실제 사용법이 어긋난 것 같을 때 사용하세요.

### 에이전트별 도구

| 에이전트 | 조회·검색 도구 | 외부 자료 조회 | Edit·Write |
| --- | --- | --- | --- |
| `researcher` | Read, Grep, Glob, Bash | WebSearch, WebFetch | 없음 |
| `planner` | Read, Grep, Glob, Bash | 없음 | 없음 |
| `reviewer` | Read, Grep, Glob, Bash | 없음 | 없음 |
| `gardener` | Read, Grep, Glob, Bash | 없음 | 없음 |

도구 목록에 Bash가 있으므로 Edit·Write가 없다는 이유만으로 파일 쓰기가 차단되지는 않습니다.
Bash를 조회에만 사용하는 것은 작업 지침입니다. 실제 실행 제한은
[지침과 기술적 제한](#지침과-기술적-제한)을 확인하세요.

## 전체 작업 흐름

### 1. 이슈 준비

새 작업을 등록하려면 이슈 작성을 요청합니다. `issue` 스킬은 `paths.issueTemplates`의 양식과
`paths.conventions`의 규칙을 읽고 열린 이슈와 닫힌 이슈를 확인해 중복을 피합니다. 새 요구사항은
배경, 범위, 제외 범위와 확인 가능한 완료 조건으로 작성합니다. 이미 끝난 작업을 기록한다면
수행한 변경과 검증만 과거형으로 적으며, 끝난 일을 예정된 작업처럼 쓰지 않습니다.

이슈 게시, 라벨·담당자 지정과 이슈 관계 변경은 사용자가 요청한 범위에서만 수행합니다. 게시한
경우 생성된 이슈를 다시 조회해 제목, 본문과 메타데이터를 확인하며, 응답이 불명확하면 생성
여부를 먼저 확인해 같은 이슈를 중복 생성하지 않습니다.

### 2. 조사, 계획과 구현

기존 이슈로 작업할 때는 `/dev-cycle <이슈 번호>`를 사용합니다. 이 명령은 다음 순서로 진행합니다.

1. 이슈 범위, 설정의 저장소와 실제 작업 저장소를 확인합니다.
2. researcher가 현재 구현과 요구사항을 조사합니다.
3. planner가 변경 파일, 단계, 위험과 검증 계획을 작성합니다.
4. 현재 브랜치와 작업 트리를 확인해 기존 변경을 보존하고, 저장소 규칙에 맞는 작업 브랜치에서
   승인된 범위를 구현합니다. 기본 브랜치에는 직접 구현하지 않습니다.
5. `/test`로 변경에 맞는 테스트를 실행합니다.
6. reviewer가 기준 ref와 변경을 검토합니다. 승인 범위 안의 명백한 문제는 수정하고 다시
   검증하며, 새 설계나 범위 확대가 필요한 지적은 결정 사항으로 분리합니다.
7. CLI `report`로 PR 검증 블록을 만들고 확인된 작업을 정리합니다.

이미 승인된 로컬 구현과 실패 수정은 반복해서 확인하지 않고 이어갑니다. 브랜치 규칙이나 비교
ref가 없거나 기존 변경 때문에 안전하게 작업 브랜치를 준비할 수 없다면 임의로 진행하지 않고
문제를 보고합니다.

### 3. 테스트와 실행 증거

`/test`는 먼저 `dev-cycle test --dry-run --json`으로 선택할 Gradle 태스크와 이유를 확인한 뒤
실제 테스트를 실행합니다. CLI가 없다면 `commands.test`의 실행 파일과 인자 배열을 유지해 직접
실행할 수 있지만, 그 결과를 CLI 기록이나 코드 지문이 있는 것처럼 표현하지 않습니다.

실제 종료 코드, 시작과 종료 시각, 실행한 인자, 테스트 결과와 테스트 전후 코드 상태를
확인합니다. 명령을 호출했다는 기록이나 과거 결과 파일은 성공 증거가 아닙니다. 캐시,
`UP-TO-DATE`, `NO-SOURCE`와 테스트 0개도 새 테스트가 통과한 것으로 세지 않습니다.

CLI `report`는 가장 최근에 시작한 실행의 상태와 현재 코드의 신선도를 Markdown으로 만듭니다.
테스트를 다시 실행하지 않으며, 최신 실패나 중단을 과거 성공으로 가리지 않습니다. 테스트 뒤
코드가 바뀌었으면 다시 실행하거나 현재 코드가 검증되지 않았다는 문구를 유지합니다.

### 4. 로컬 변경 리뷰와 원격 PR 리뷰

`reviewer`와 `/review-pr`은 검토 대상이 다릅니다.

| 기능 | 검토 대상 | 결과 |
| --- | --- | --- |
| `reviewer` | 구현 중인 로컬 작업 트리와 기준 ref의 차이 | 구현자가 반영할 Must/Should/Nit 지적 |
| `/review-pr <번호>` | 원격 PR의 현재 head와 diff | 게시할 수 있는 리뷰 코멘트 제안 |

`/review-pr`은 PR 제목, 본문, head SHA와 diff를 조회하고, 코멘트 위치를 현재 head의 실제 파일과
대조합니다. 먼저 코멘트 제안만 만들며, 사용자가 게시할 항목을 지정했거나 게시가 요청 범위에
포함된 경우에만 해당 코멘트를 게시합니다. 리뷰를 위해 fetch가 필요하면 기존 작업 트리를
보존하고 임의로 체크아웃하지 않습니다.

### 5. 커밋과 PR 작성

한 번의 `/dev-cycle`은 지정한 이슈의 범위를 작업 단위로 삼습니다. 브랜치 이름과 커밋 메시지
형식은 `paths.conventions`가 가리키는 저장소 지침을 따릅니다. 커밋과 push는 메인 대화에서
요청한 범위에만 수행하며, 실제 변경을 확인해 작업 내용에 맞는 단위로 커밋합니다. 리뷰 반영
후 코드가 달라졌다면 커밋 전에 다시 검증합니다.

PR 작성을 요청하면 `pr` 스킬이 현재 브랜치, 기준 ref 이후 커밋과 diff, 관련 이슈와
`paths.prTemplate`의 양식을 확인합니다. CLI가 있으면 `report --json`으로 최신 실행 상태와 현재
코드의 신선도를 확인합니다. PR 본문에는 실제 변경과 실행한 검증만 적고, 미실행 항목은 이유를
남깁니다. report 생성 성공 자체를 테스트 통과로 해석하지 않습니다.

현재 브랜치가 기본 브랜치이거나 기준 ref 이후 커밋이 없으면 상태를 보고하고 PR을 게시하지 않습니다.

push, PR 게시, 라벨·리뷰어 지정은 사용자가 요청한 범위에서만 수행합니다. 게시한 뒤에는 PR을
다시 조회해 head, base, 제목, 본문과 메타데이터를 확인합니다.

### 6. 리뷰 반영

PR 리뷰 반영을 요청하면 `apply-review` 스킬이 현재 브랜치와 PR head가 같은지 먼저 확인하고,
모든 페이지의 미해결 리뷰 스레드를 읽습니다. 코멘트의 과거 diff 위치를 그대로 믿지 않고 현재
파일에 다시 연결한 뒤 다음처럼 분류합니다.

- 수용: 현재 코드에도 문제가 있으며 요청 범위 안에서 수정할 수 있습니다.
- 거절: 현재 코드에 적용되지 않거나 다른 근거가 있어 반영하지 않습니다.
- 보류: 새 설계 결정, 범위 확대나 추가 정보가 필요합니다.

사용자가 이미 수용·거절 범위를 지정했다면 수용 항목을 좁게 수정하고 `/test` 규칙에 따라 다시
검증합니다. 판단이 남은 항목만 질문합니다. push, 답글과 스레드 resolve 역시 요청된 항목에만
수행하며 해결된 스레드나 후속 답글을 중복 처리하지 않습니다.

### 7. 세션 재개와 마무리

긴 작업은 [작업 맥락 메모](../.claude/claude-progress.txt.example)와
[작업 목록 예시](../.claude/feature_list.json.example)를 복사해 개인 파일로 관리할 수 있습니다.
`/resume`은 이 메모와 현재 브랜치, 작업 트리, 기준 ref, 최근 커밋과 이슈 상태를 대조하고 다음
작업 하나를 제안합니다. 메모가 없으면 예제 위치만 안내하며 자동으로 만들지 않습니다. 내용이
오래됐거나 충돌하면 Git과 이슈 상태를 우선합니다.

작업 맥락 메모에는 현재 브랜치, 관련 이슈, 지금 하는 일, 직전에 끝낸 일, 다음 작업과 막힌 점을
적습니다. 작업 목록에는 각 항목의 설명과 `todo`/`doing`/`done` 상태를 기록합니다. `/resume`은
`doing` 항목을 우선하고, 없으면 `todo`에서 다음 작업을 제안합니다. 코드·커밋·브랜치를
변경하지 않으며 실제 구현은 요청 범위를 정해 `/dev-cycle`로 이어갑니다.

`/wrap-up`은 현재 대화, Git 상태와 실제 검증 기록에서 완료한 일, 결정, 변경, 검증 결과, 다음
작업과 미해결 사항을 로컬 요약으로 만듭니다. 외부 서비스로 전송하지 않으며 확인되지 않은
결과를 채우지 않습니다. 실제 메모는 Git에서 제외되는 보조 자료이고 승인, 테스트 성공이나
여러 기기의 공유 상태를 나타내는 기준이 아닙니다.

`/wrap-up`이 메모 파일을 자동으로 갱신하지는 않습니다. 요약을 보고 사용자가 필요한 내용을
메모에 옮길 수 있습니다.

## 현재 지원 상태

현재 CLI는 배포용 템플릿과 설정을 검사하고 `init`으로 설치합니다. `test`는 정적 Groovy
`settings.gradle`의 최상위 모듈을 선택해 루트 Gradle Wrapper로 실행하고
`<artifactsDir>/runs/<UUID>/record.json`에 기록합니다. `report`는 최신 기록과 현재
코드/설정을 비교해 PR 본문용 Markdown을 stdout으로 출력합니다.

먼저 `dev-cycle test --dry-run --json`으로 선택 결과와 이유를 확인한 뒤
`dev-cycle test --json`으로 실행하세요. `--base-ref`로 비교 ref를 지정할 수 있습니다.
지원하지 않는 동적 설정, projectDir, composite build, Kotlin DSL을 발견하면 중단합니다.
기본 실행 파일은 `./gradlew`, Windows에서는 `./gradlew.bat`입니다. args의 `test` 하나를
선택된 태스크로 바꾸고 `--console=plain`, `--no-daemon`을 사용합니다. Windows 경로에
따옴표, `% ! ^ & | < > ( )`, 줄바꿈이 있으면 실행 전에 거부합니다. 공백과 한글은
지원합니다. CLI가 없는 환경에서는 `/test`의 직접 실행 절차를 따르되 CLI 기록이 있다고
표시하면 안 됩니다.

실행 상태, 종료 코드, 이번 실행의 XML 결과, 코드 지문을 구분합니다. 코드 지문은 테스트 당시
파일 상태를 나중에 비교하기 위한 SHA-256 해시입니다. 캐시/UP-TO-DATE/NO-SOURCE는 새 테스트
실행이 아닙니다. 실행 전후나 이후에 코드가 바뀌면 이전 결과를 현재 코드의 통과로 사용하지
않습니다. stdout/stderr는 각각 앞 1 MiB까지만 로컬에 보관합니다. 종료 기록이 없는 run은
미완료로 처리합니다.

`dev-cycle report`는 기본적으로 가장 최근에 시작한 기록을 선택합니다. 최신 실패/중단 기록을
과거 성공 기록으로 바꾸지 않으며, 잘못된 run 디렉터리나 손상된 기록을 건너뛰지 않습니다.
`--run-id`로 유효한 UUID를 지정할 수 있지만 과거 기록도 현재 코드와 다시 비교합니다. 기록이
없으면 미실행으로 표시합니다. 저장된 합계에 없는 실패 이름, 커버리지, 수동 시연, 원격 CI
결과는 추정하지 않습니다.

기본 출력은 stdout으로 보내는 Markdown입니다. `--json`은 Markdown, 선택한 실행 기록,
신선도를 JSON 객체 하나로 출력합니다. 신선도는 테스트 당시 코드와 현재 코드가 같은지를
뜻합니다. `--output`은 `<artifactsDir>/reports/` 아래의 새 Markdown 파일만 허용하며 기존
파일, 링크, 추적 파일을 덮어쓰지 않습니다. `--dry-run`은 파일과 디렉터리를 만들지 않습니다.
report가 `changed`, `unknown`, `incomplete`를 표시하면 `/wrap-up`과 PR 스킬도 현재 코드를
검증하지 않았다는 표시를 유지합니다.

## 실패와 재개

- 명령을 시작하지 못했다면 미실행으로 기록합니다.
- 실제 종료 코드가 실패라면 실패로 기록하고, 원인을 고친 뒤 새 실행으로 검증합니다.
- 취소나 신호로 끝났다면 중단으로 기록합니다.
- 문서 변경처럼 설정된 규칙에 따라 테스트하지 않았다면 생략 사유를 적습니다.
- 세션을 다시 열 때 `/resume`은 개인 메모를 Git과 이슈 상태에 대조합니다. 메모가 오래됐다면
  Git과 원격 상태를 우선합니다.

성공, 실패, 중단, 생략, 미실행을 서로 바꿔 쓰지 않습니다. `PreToolUse`는 호출 전 입력만
기록하므로 프로세스 완료나 테스트 성공을 확인하는 자료가 아닙니다. 테스트 이후 코드가
바뀌었거나 당시 상태와 같은지 확인할 수 없으면 다시 검증하거나 현재 코드를 검증하지
않았다고 표시합니다. 예전 성공 결과를 현재 변경의 성공 결과로 사용하지 않습니다.

로컬 테스트가 실패하면 오류와 실패한 태스크를 확인하고 원인을 좁혀 수정한 뒤 새 실행으로
검증합니다. 리뷰 지적을 반영한 뒤에도 같은 절차를 반복합니다. 원격 CI는 로컬 실행과 별개의
결과이므로 실패한 job의 로그를 확인하고, 수정과 로컬 검증 후 CI를 다시 실행합니다. 로컬
report에 없는 CI 결과를 추정해 넣거나 CI 통과를 로컬 테스트 기록으로 바꾸지 않습니다.

## 지침과 기술적 제한

에이전트 문서의 “Bash는 조회에만 사용한다”는 작업 지침입니다. 도구 목록에 Bash가 있으면
문장만으로 파일 쓰기를 막을 수는 없습니다. 실제 제한은 Claude Code 권한 규칙, 운영체제
권한, 샌드박스, 차단 hook으로 설정해야 합니다.

공유 `settings.json`은 plan 기본값만 제공합니다. 개인 `settings.local.json`의 권한을
자동으로 추가하거나 넓히지 않습니다. hook을 추가한다면 호출 전 로그와 실행 후 결과를
구분하고, 로깅 실패를 테스트 성공으로 해석하지 마세요.

## 작업 메모

`.claude/claude-progress.txt.example`과 `.claude/feature_list.json.example`만 공유합니다. 실제
파일은 기기에만 두는 보조 자료이며 Git에서 제외합니다. 승인 상태, 검증 결과, 여러 기기
사이의 공유 상태를 메모로 관리하지 않습니다.

```sh
claude plugin install mattpocock-skills@claude-plugins-official
```

플러그인 설치와 파일 복사 방식 중 하나만 선택하세요. 파일을 복사한다면 `grill-me`가 의존하는
`grilling`도 함께 설치해야 합니다. 설치하지 않았다면 planner 결과에 남은 결정을 일반 질문으로
확인하세요. dev-cycle 템플릿은 두 스킬의 본문을 재배포하지 않습니다.
